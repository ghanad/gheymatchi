# PostgreSQL Migration Plan

GheymatChi still uses SQLite for the local MVP. This document records the current SQLite assumptions and the changes needed before a future PostgreSQL migration. It does not add PostgreSQL as a runtime dependency.

## Current Schema Review

The SQLite schema is managed by SQL files in `backend/migrations` and applied by the Go migrator in `backend/internal/db`.

Current tables:

- `users`: text IDs, unique email, UTC text timestamps.
- `products`: text IDs, optional `user_id`, nullable description, UTC text timestamps.
- `product_sources`: text IDs, product foreign key, URL, source name, integer boolean `is_active`, unique `(product_id, url)`.
- `price_points`: text IDs, product and source foreign keys, integer IRR price, optional raw payload, optional derived decimal text values, UTC text timestamps.
- `market_rates`: text IDs, rate type, unit, decimal text value, UTC text timestamps.
- `alerts`: text IDs, optional user and product foreign keys, alert condition fields, decimal text threshold, integer boolean `is_active`, optional `last_triggered_at`, UTC text timestamps.
- `notifications`: text IDs, optional alert foreign key, channel, recipient, status, optional `sent_at`, UTC text timestamp.
- `crawl_runs`: text IDs, optional source foreign key, status, optional error message, UTC text timestamps.
- `schema_migrations`: migration name, checksum, and UTC text applied timestamp.

Current indexes cover the main access paths:

- Products by `user_id`.
- Sources by `product_id`.
- Price points by `(product_id, captured_at)` and `(product_source_id, captured_at)`.
- Market rates by `(rate_type, observed_at)`.
- Alerts by `product_id`.
- Notifications by `alert_id`.
- Crawl runs by `(source_id, started_at)`.

## PostgreSQL Differences That Matter

### Timestamp Handling

SQLite stores timestamps as UTC RFC3339/RFC3339Nano text. PostgreSQL should use `TIMESTAMPTZ` for all timestamp columns. Application code should continue normalizing times to UTC at boundaries, but PostgreSQL can own timestamp comparison and ordering with native types.

Before migrating:

- Keep API responses unchanged unless a later phase explicitly changes the contract.
- Backfill by parsing existing timestamp text as UTC.
- Decide whether `schema_migrations.applied_at` should also become `TIMESTAMPTZ`.

### Numeric And Decimal Handling

IRR prices are currently stored as integers in `price_points.price_irr`, which maps cleanly to PostgreSQL `BIGINT`.

Decimal-safe values are currently stored as text:

- `market_rates.value_text`
- `alerts.threshold_value_text`
- `price_points.usd_irr_rate_value_text`
- `price_points.gold_gram_irr_rate_value_text`
- `price_points.price_usd`
- `price_points.price_gold_gram`

PostgreSQL should use `NUMERIC` for these columns once precision and scale expectations are known. Until then, text storage is acceptable because validation happens in domain code with decimal parsing and no floating point storage.

Before migrating:

- Confirm maximum expected precision for currency rates and gold units.
- Convert valid decimal text to `NUMERIC`.
- Keep `price_irr` as `BIGINT`, not `NUMERIC`, unless the domain model changes.

### Indexes

The current indexes are portable and should be recreated in PostgreSQL. PostgreSQL may later benefit from descending indexes for latest-row queries, but the first migration should preserve the current query behavior before optimizing.

Likely PostgreSQL indexes:

- `products(user_id)`
- `product_sources(product_id)`
- `price_points(product_id, captured_at)`
- `price_points(product_source_id, captured_at)`
- `market_rates(rate_type, observed_at)`
- `alerts(product_id)`
- `notifications(alert_id)`
- `crawl_runs(source_id, started_at)`

After migration, inspect query plans for:

- Latest market rate by `rate_type` and `observed_at <= captured_at`.
- Price history by product ordered by capture time.
- Worker source listing with `is_active = true`.

### Constraints

SQLite currently enforces primary keys, foreign keys, uniqueness, and `NOT NULL` constraints. Boolean-like values are stored as integers because SQLite has no strict boolean type.

PostgreSQL should strengthen constraints where they map directly to existing domain validation:

- Use `BOOLEAN` for `product_sources.is_active` and `alerts.is_active`.
- Keep foreign key actions equivalent to the SQLite schema.
- Preserve `UNIQUE (product_id, url)` on `product_sources`.
- Add `CHECK` constraints only for already-established invariants, such as `price_irr > 0`, known status values, known alert condition types, known notification channels/statuses, and positive numeric text after conversion to `NUMERIC`.

Do not add new constraints that would reject data accepted by the current application without a cleanup migration first.

### ID Strategy

IDs are generated by application code as 16 random bytes encoded as lowercase hex text. PostgreSQL can keep these as `TEXT` for the first migration to avoid changing API contracts and foreign key data.

A later phase may move to UUIDs, but that should be a separate change because it touches every table, API payload, seed data, tests, and frontend assumptions.

Recommended first PostgreSQL migration:

- Keep IDs as `TEXT PRIMARY KEY`.
- Keep application-generated IDs.
- Consider a later UUID migration only after the PostgreSQL migration is stable.

## SQLite-Specific Code

SQLite-specific code is intentionally isolated:

- `backend/internal/db/db.go`: imports `modernc.org/sqlite`, opens the `sqlite` driver, configures PRAGMA settings, uses a file path from `DB_PATH`, and limits open connections for local SQLite behavior.
- `backend/internal/db/migrate.go`: uses `?` placeholders and stores migration timestamps as text. The migration runner itself is mostly generic, but the placeholder style is SQLite-specific.
- `backend/internal/*/sqlite_store.go`: repository implementations use SQLite SQL and `?` placeholders.
- `backend/migrations/*.sql`: migration SQL is written for SQLite. The `ALTER TABLE ... RENAME COLUMN` and table rebuild pattern in `003_price_points_phase7.sql` should not be reused as-is for PostgreSQL.
- Tests with in-memory SQLite helpers and `sqlite_master` checks are SQLite-specific by design.
- Docker Compose services mount `./data:/data` and use `DB_PATH=/data/gheymatchi.db`.

Business logic remains database-agnostic:

- HTTP handlers depend on store interfaces or concrete stores only at composition time.
- Worker logic depends on small interfaces for source listing, price creation, crawl tracking, alert evaluation, and notification processing.
- Domain validation uses Go types and decimal-safe parsing, not SQLite-specific behavior.

## Migration Path

1. Keep the SQLite schema as the source of truth until a dedicated PostgreSQL phase.
2. Add a PostgreSQL connection package beside the SQLite opener instead of replacing `backend/internal/db/db.go` immediately.
3. Add PostgreSQL migrations in a separate directory, for example `backend/postgres_migrations`, so SQLite migrations remain runnable for local MVP development.
4. Create PostgreSQL store implementations behind the existing domain interfaces.
5. Add integration tests for PostgreSQL stores while keeping SQLite tests.
6. Add a one-time data migration command that reads SQLite rows and writes PostgreSQL rows with explicit type conversions.
7. Run both implementations against the same business-level store tests where practical.
8. Switch Docker Compose to PostgreSQL only in the future phase that explicitly introduces PostgreSQL.

## Initial PostgreSQL Type Mapping

| Current SQLite shape | PostgreSQL first target | Notes |
| --- | --- | --- |
| `TEXT PRIMARY KEY` IDs | `TEXT PRIMARY KEY` | Preserve API contracts first. |
| UTC timestamp `TEXT` | `TIMESTAMPTZ` | Parse existing values as UTC. |
| IRR `INTEGER` | `BIGINT` | No floating point values. |
| Decimal text | `NUMERIC` | Confirm precision before converting. |
| Boolean integer `0/1` | `BOOLEAN` | Convert `0` to false, `1` to true. |
| Raw payload `TEXT` | `TEXT` or `JSONB` | Use `JSONB` only after validating payload shape. |
| `?` placeholders | `$1`, `$2`, ... | Store implementations must be driver-specific. |

## Schema Cleanup Decision For Phase 20

No schema migration is added in this phase. The current schema already avoids the highest-risk PostgreSQL migration problems:

- IDs are application-generated and portable.
- Prices are not stored as floating point values.
- Decimal values are stored losslessly as text.
- Store interfaces keep database details out of business logic.
- Existing indexes match current query paths.

The main cleanup opportunities, such as boolean `CHECK` constraints and stricter status constraints, are better handled during the PostgreSQL schema creation or in a dedicated SQLite hardening phase with data validation.
